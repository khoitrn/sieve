## Last completed

Built and deployed `sieve-registry` (new repo, Cloudflare Worker + D1, `https://sieve-registry.khoitrn.workers.dev`) — a central database of the skill catalog that `sieve init` pulls a recommended shortlist from, instead of always copying every skill. Added `scripts/onboard.mjs` as the new default `init` path: a short interview (new idea vs existing project, focus keywords), a call to the registry's `/api/recommend` (rule-based tag matching, no ML/LLM scoring in v1), selective install of just guardrails + the matched shortlist, and an assignment record written back to the registry (`/api/projects/:id/assign`). `scripts/init.mjs` (full bundled catalog, no prompts, no network) is preserved as the `--all`/`--offline` path for CI/scripted use, since Sieve must keep working with zero network access.

Then extended the registry from one hardcoded source (sieve itself) to many: a `sources` table (curated vs. user-added, namespaced `(source_id, name)` so two sources can share a skill name), a generic `SKILL.md` scanner for repos that don't publish `sieve.index.json` (evaluated `obra/superpowers` as the first real external source), external skills always forced to `tier: "catalog"` regardless of their own frontmatter (only sieve's own repo may ship guardrails), and identity resolved per-request from a GitHub bearer token (no sessions, matching sieve-dashboard's existing design) so a user's own connected sources stay private to them. Shipped a Sources tab in sieve-dashboard — first real use of the sign-in flow built earlier, previously wired but unused for anything stateful.

Caught two real security/correctness bugs via live testing against the deployed Worker before calling any of this done: `deleteSource` originally deleted a source's skill rows *before* checking ownership, so a rejected/unauthorized delete attempt still wiped content; the naive fix (check ownership first) then violated the `skills → sources` foreign key on legitimate deletes. Fixed by verifying ownership with a read-only `SELECT` first, then deleting children before parent only if authorized — both the vulnerability and the FK violation were reproduced live and re-verified fixed, not just reasoned about.
